# Задания для разработчиков

## Цель

Создать эффективный и проверяемый харнесс агента для извлечения данных экспериментов из разрешённых научных статей и книг: текста, таблиц, графиков, изображений и сканов. Результат должен быть пригоден для экспертной проверки, а не только для автоматической генерации ответа.

Работа ведётся через pull request в этот репозиторий. Прямые изменения `main` не допускаются.

## Состав групп

### Группа B — data engineering и оцифровка

**P03, P04, P06, P07, P12, P18**  
Координатор: **P07**. Резерв по доступности: **P06**.

1. **Ingestion manifest.** Описать и реализовать схему входного разрешённого документа: идентификатор, путь, тип, статус прав на обработку.
2. **Текст и OCR.** Сделать адаптер, который извлекает кандидаты из текста/скана и сохраняет страницу и точный локатор фрагмента.
3. **Таблицы.** Реализовать извлечение значений, заголовков и единиц из тестового табличного примера.
4. **Графики и рисунки.** Спроектировать представление области изображения, осей и ряда данных; каждый результат обязан ссылаться на рисунок и область.
5. **Журнал запуска.** Сохранять воспроизводимый JSONL-журнал без токенов, исходных промптов с секретами и персональных данных.

### Группа C — ML, оркестрация и оценка

**P02, P09, P10, P11, P15, P17**  
Координаторы: **P11/P17**. Поддержка по доступности: **P02**.

1. **Цикл харнесса.** Реализовать минимальный путь: извлечение → валидация → запрос экспертного ревью.
2. **Нормализация.** Нормализовать имена переменных и единицы, сохраняя исходное значение и единицу для проверки.
3. **Политика уверенности.** Сделать объяснимый confidence score; слабый или отсутствующий локатор должен снижать уверенность.
4. **Оценочный набор.** Подготовить обезличенные JSONL-fixtures и локальный отчёт метрик для сравнения версий харнесса.
5. **Ревью кандидатов.** Создать минимальный CLI/интерфейс для approve/reject с комментарием эксперта и сохранением provenance.

## Общие критерии готовности

Для каждого извлечённого значения обязательны: `document_id`, страница, modality, locator, поле, значение, единица, confidence и review status. Если доказательство неоднозначно, агент создаёт `candidate`, а не утверждает значение.

Каждая задача оформляется отдельным небольшим PR:

1. создать ветку `feature/<краткое-имя>`;
2. добавить/изменить тест или воспроизводимый fixture;
3. выполнить `pytest`;
4. в PR указать цель, входной пример, ожидаемый результат, проверку, ограничения;
5. запросить ревью у другой группы и эксперта при изменении схемы данных.

## Ограничения безопасности и прав

- Не коммитить токены, `.env`, контакты, опросы участников, приватные сессии и неразрешённые PDF/книги.
- Обрабатывать только материалы с подтверждённым правом на использование.
- Не удалять provenance при нормализации и не заменять неопределённость выдуманным значением.
- Любой внешний сервис использует секреты только из локального окружения; секреты не попадают в Git, issue или PR.
